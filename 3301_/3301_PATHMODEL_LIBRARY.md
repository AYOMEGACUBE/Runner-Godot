# 3301 PATHMODEL LIBRARY

**Актуально:** 2026-04-15.

## Компоненты

- **`scripts/path/PathModel.gd`** — модель, `bake_from_steps`, `validate_full`, `resolve_platform_overlaps`, `smooth_path`.
- **`scripts/path/PathLibrary.gd`** — загрузка JSON или `_build_models_deterministic(3301)`.
- **`scripts/path/PathSelector.gd`** — `initialize()`, `select_model_for_run()`, `next_step()` (для инструментов/тестов; уровень в основном использует bake).

## Структура PathModel (данные)

- `model_id: int`
- `trend_degrees: float` (метаданные; bake опирается на шаги)
- `steps: Array` словарей:
  - `x_gap: float` — clamp к `[min_gap, max_gap]` из `platform_rules.json`
  - `y_delta: float` — clamp к `[-height_variation, height_variation]`
  - `wave_id: int` — при смене относительно предыдущего шага инвертируется направление по X
  - `decoy_count: int` — используется если нет явного `size`
  - **`size: String`** (опционально) — `small` | `medium` | `large` → ширина 64 / 128 / 256 px (при тайле 64)

## Выпеченные слоты (`platforms[]`)

После bake: `{ "x", "y", "segments", "vanish" }`. `Level` размещает ноды платформ по слотам из пула.

## Хранилище библиотеки

- **Файл:** `res://DATA/PulseRunnerData/path_library_50.json` — массив из объектов-моделей (желательно **50** штук).
- **`PathLibrary.load_all()`:** если после парсинга `models.size() > 0`, библиотека принимается; если не 50 — предупреждение в консоль.
- Если JSON невалиден/отсутствует — полная пересборка 50 моделей кодом (не загрузка с диска).

## Выбор модели на забег

- `PathSelector.select_model_for_run()` — `rng = SeedManager.get_rng_for("path")`, индекс `0 .. size-1`.
- Направление старта по X: чётность `(global_seed ^ model_id)`.

## Правила bake (из `platform_rules.json`)

Ключевые параметры (неполный список): `min_gap`, `max_gap`, `height_variation`, `safe_margin_x`, `vanish_chance`, `jump_reach_max_fraction`, `min_edge_gap`, `vertical_gap`, `path_min_horizontal_span_ratio`, `path_bake_max_iterations`, `path_bake_max_slots`, `path_bake_min_steps_before_span_ok`.

Подробности досягаемости и анти-overlap — в коде `PathModel.gd` и в комментариях к правилам.

## Вводная для расстановки платформ / генерации пути (эталон)

Ниже — **полный набор данных**, по которому можно однозначно строить путь (для человека, ИИ или внешнего генератора). Твои пункты 1–8 дополнены системой координат, точками A/B, трактовкой прыжка и связью с рантаймом.

### A. Мир и координаты (обязательно)

1. **Система координат:** Godot 2D — ось X вправо, **Y вниз** (больше Y = ниже по экрану). «Подъём пути» = **уменьшение** Y у следующих опорных платформ.
2. **Ширина мира:** 153 600 px → границы по X: обычно `min_x = 0`, `max_x = 153 600` (центры платформ так, чтобы AABB платформы не выходила за эти границы).
3. **Высота мира:** 153 600 px → `max_y − min_y = 153 600`; конкретные `min_y` / `max_y` нужно задать относительно **стартовой позиции героя** или первой платформы (как в `Level._setup_world_bounds`: низ от игрока + pad, верх = низ − 153 600).
4. **Точка A (старт пути):** центр первой платформы `(x_A, y_A)`, тип ширины (`small` / `medium` / `large` или число сегментов), направление бега по X (`+1` / `−1`).
5. **Точка B (конец отрезка для угла 5°):** либо координаты `(x_B, y_B)` **центра последней** платформы участка, либо вектор смещения `(Δx, Δy)` от A к последней опорной платформе. Без B **нельзя** формально проверить «общий угол подъёма ≈ 5°».

**Угол подъёма при Y вниз:** для средней линии от A к B  
`angle_up = atan2(Δx, -(y_B - y_A))` в радианах (горизонталь vs подъём по экрану), либо эквивалентно через `atan2(-(y_B-y_A), Δx)`. Требование: **средний угол ≈ 5°** (уточнить: в градусах, в плоскости экрана, по **центрам** платформ по порядку пути).

### B. Герой и прыжок (обязательно)

6. Либо **тройка** `GRAVITY`, `JUMP_VELOCITY`, `MOVE_SPEED`, либо сразу **производные:** макс. высота прыжка ≈ **230 px**, макс. горизонталь при «ровной» паре поверхностей ≈ **336 px** (как в `PhysicsConfig`; фактическая досягаемость по X **зависит от ΔY** между поверхностями — см. ниже).
7. **Доля досягаемости в правилах** (если как в игре): `jump_reach_max_fraction` (например 0.8) — запас при валидации прыжка между соседними слотами.

### C. Платформы (обязательно)

8. **Типы поведения:** обычная; осыпающаяся; decoy / fake **без коллизии** с героем.
9. **Типы по ширине:** small / medium / large → **64×64, 128×64, 256×64** px (высота одна, ширина кратна 64).
10. **Кодирование для движка:** обычная / crumble → флаг `vanish` или `is_crumbling`; decoy/fake — **отдельные** слоты или поля (`is_decoy`, `fake_visual_only`), не участвующие в коллизии с героем; при генерации пути явно указать, **какие индексы** — только визуал.

11. **Не одна линия (предзаданная карта в библиотеке):** уровень не сводится к одной цепочке платформ.
    - **Опорный маршрут** — единственная проходимая цепочка (`support_chain_indices`); остальные decoy **недостижимы** с любой опорной (запас по reach / по вертикали).
    - **Ложные платформы** размещаются **выше и ниже** полосы маршрута (в координатах Godot: меньше Y = выше на экране), не «в коридоре» между двумя опорными на одной высоте.
    - По **опорной** цепи герой и **поднимается**, и **опускается** (чередование шагов по Y, без длинной монотонности только вверх).

### D. Экран и видимость (обязательно для «не более 8»)

12. **Логический размер экрана (эталон UI/камеры):** `BASE_WIDTH = 1080`, `BASE_HEIGHT = 1920` — как в `MobileUIScale.gd`; это **не** размер мира 153600, а масштаб отображения.
13. **«Одновременно вокруг героя не более 8 платформ»** нужно определить численно:
    - либо **все платформы**, чьи AABB пересекают прямоугольник **видимой области** (viewport) с запасом,
    - либо только **опорные** (не decoy),
    - либо радиус в **мировых px** от героя (например, половина высоты экрана в мировых единицах после масштаба).  
    Без этого условие не проверяется однозначно.

### E. Геометрия пути (твои условия + уточнения)

14. **Вертикаль:** от локального «уровня» соседних опорных платформ допускается смещение **до ±900 px** (уточнить: от предыдущей **поверхности** или от **центра**; в коде близко к clamp `y_delta` к диапазону вроде `height_variation`).
15. **Не касаются друг друга:** минимальные зазоры **по X между краями** и **по Y между AABB** (в игре: `min_edge_gap`, `vertical_gap`); «не касаются» = нет пересечения прямоугольников с учётом этих зазоров.
16. **Расстояние между платформами 40%–90% от макс. прыжка** — зафиксировать трактовку:
    - **Рекомендуемый смысл:** горизонтальное расстояние **между ближайшими краями** соседних опорных платформ вдоль пути, в диапазоне `[0.40 × R_ref, 0.90 × R_ref]`, где `R_ref` — эталонная горизонтальная досягаемость (например **336 px** при выбранном эталонном **ΔY между поверхностями**, часто 0).
    - **Обязательное дополнение:** для **каждой** пары соседних **опорных** по порядку проверить **достижимость прыжка** с учётом реального `ΔY` (как `PhysicsConfig.horizontal_reach_surface_to_surface` + `safe_margin_x` и `jump_reach_max_fraction`). После вставки decoy между опорными в списке `platforms[]` пересчитывать **X** опорных так, чтобы пары в `support_chain_indices` по-прежнему удовлетворяли gap и reach.
17. **«Хаотично, но с правилами»:** задать **seed** (детерминизм), диапазоны/распределение для `x_gap`, `y_delta`, выбора `size`, выбора типа (обычная / crumble / decoy), и запрет на повторяющиеся шаблоны (опционально).

### F. Выход генератора (что должно получиться)

18. **Упорядоченный список слотов** (порядок = порядок обхода в данных): для каждого — `x`, `y` (центр), `width` / `segments`, тип (обычная / crumble / decoy), флаги коллизии; при генерации внешней моделью допускаются `order`, `bait_band`, расширенный `meta` (см. нейтральное ТЗ **`3301_PLATFORM_LAYOUT_SPEC_FOR_LLM.txt`** в корне репозитория).
19. Для импорта в `PathModel`: массив `platforms[]` с полями `x`, `y`, `segments`, `vanish` (0/1), `is_decoy`; при смешении опорных и decoy в одном массиве задай **`support_chain_indices`** (индексы опорных по порядку пути). Поля `bait_band`, `kind`, `size`, `order` в JSON допустимы — при загрузке движок их не использует.

### Сжатая «вводная» (чеклист для ИИ)

| Блок | Что нужно |
|------|-----------|
| Мир | min/max X, min/max Y, или ширина/высота 153600 + правило якоря |
| A | (x_A, y_A), размер первой платформы, направление X |
| B | (x_B, y_B) или (Δx, Δy) для проверки ~5° |
| Физика | g, v_jump, v_x **или** H_max, W_max + эталон ΔY для W |
| Платформы | Типы, размеры 64/128/256 по ширине; crumble/decoy; **не одна линия** — недостижимые decoy сверху/снизу |
| Опорный путь | Подъём **и** спуск по Y; средний угол ~5° к финишу |
| Экран | 1080×1920 эталон; определение «вокруг героя» для лимита 8 |
| Зазоры | ±900 по вертикали; краевые зазоры; 40–90% от R_ref **и** проверка reach **по парам опорных** |
| Хаос | seed, допустимые распределения |
| Выход | Список слотов + `support_chain_indices`; опционально `bait_band`, meta-счётчики |

## Задание на внешнюю генерацию JSON

- **Нейтральное ТЗ для любой LLM** (явная карта `platforms[]` + `support_chain_indices`, физика, ограничения, формат вывода и **как встроить ответ в библиотеку**): **`3301_PLATFORM_LAYOUT_SPEC_FOR_LLM.txt`** (корень репозитория).
- Модели только с **`steps`** — как раньше: bake при старте уровня. Модель с **непустым `platforms[]`** в `path_library_50.json` — предзаданная геометрия: `Level` сдвигает первую опорную к старту и вызывает `validate_full` (прыжки по парам из `support_chain_indices`, если массив задан и в нём ≥ 2 индексов).

## Стриминг из чанков (PathManager)

- **Когда:** `Level.use_path_leg_streaming == true`, узел **`PathManager`** доступен по `path_leg_stream_node` (в `level.tscn` — `PathLegStream`).
- **Откуда данные:** JSON в `res://DATA/PulseRunnerData/chunks/*.json` (скан **`ChunkRegistry`**), не из `path_library_50.json`.
- **Цепочка:** `ChunkRegistry.reload()` → `LegBuilder.build_leg(...)` → `PlatformSpawner.spawn_leg(...)` под родителем `Platforms`.
- **RNG:** `SeedManager.get_rng_for("path_legs")`.
- **Согласованность с библиотекой:** формат объекта модели в чанке тот же класс идей, что и элемент `path_library_50.json` (см. **`3301_PLATFORM_LAYOUT_SPEC_FOR_LLM.txt`**, раздел интеграции); при отключённом стриминге правки только в `chunks/` **не** влияют на забег, пока не перенесены в библиотеку или не включён флаг.

## Ограничения рантайма

- В режиме **библиотеки** отдельного файла карты уровня нет: траектория — через элементы **`path_library_50.json`** (или bake из `steps`).
- В режиме **чанков** карта не в одном массиве из 50: набор файлов в **`chunks/`**, по одному `model_id` на зарегистрированную модель (последний файл с тем же `model_id` перезаписывает предыдущий в памяти).
- Слишком короткая библиотека (< 50 моделей) уменьшает разнообразие забегов, но допустима.
