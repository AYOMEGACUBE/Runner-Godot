# 3301 TECH AUDIT + MVP PLAN (One-pass)

**Актуально:** 2026-04-15  
**Формат:** один проход, без рефакторинга кода, фокус на архитектуре и рисках релиза.

## 1) Реальное состояние проекта (AS-IS)

### Ключевые модули

- **Core run-loop:** `scripts/Level.gd`, `scripts/Player.gd`, `scripts/path/*`, `scripts/managers/PathManager.gd`
- **UI flow:** `MainMenu.gd`, `GameOver.gd`, `Profile.gd`, `Champions.gd`, `HUD.gd`
- **Wall/cube subsystem:** `CubeView.gd`, `wall/wall.gd`, `wall/WallRenderer.gd`, `wall/data/WallData.gd` — актуальная схема потоков/JSON: **`3301_WALL_RENDERING_AND_STREAMING.md`**
- **Economy/purchases:** `autoload/EconomyManager.gd`, `scripts/purchase/PurchaseManager.gd`, `scripts/platform/PlatformDataStore.gd`
- **Data/auth/sync:** `scripts/DataManager.gd`, `scripts/auth/AuthService.gd`, `scripts/auth/FirebaseGoogleAuth.gd`, `scripts/sync/EconomyRemoteSync.gd`, `scripts/sync/OwnershipRemoteSync.gd`

### Архитектурный профиль

- Проект **сильно stateful**, центр тяжести в autoload-синглтонах (`GameState`, `DataManager`, `EconomyManager`, `PurchaseManager`, `AuthService`, `EconomyRemoteSync`).
- `CubeView.gd` выполняет роль **god-object**: UI + ввод + бизнес-логика покупок + интеграция с подсистемами стены/экономики.
- Есть два независимых генератора пути:
  - **Library mode** (`PathLibrary` + `PathModel` bake) — используется по умолчанию.
  - **Chunk streaming mode** (`PathManager`) — включается флагом.
- Документация в целом подробная, но есть существенные рассинхроны с фактическим кодом.

### Внешние зависимости

- Godot 4.5 (Forward Plus).
- Firebase RTDB + Firebase Auth REST.
- GitHub raw-data (`PulseRunnerData`) для `DataManager`.
- Локальный `git` как внешняя зависимость для sync в релизном контуре не требуется (primary — RTDB).
- Android addon-заготовка: `addons/android_google_signin`.

## 2) Технические проблемы (говнокод и риски)

## Критические (блокируют безопасный MVP)

1. **Sync pipeline**
   - Primary runtime sync выполняется через RTDB (`EconomyRemoteSync` + `OwnershipRemoteSync`).
   - Риск: обработка конфликтов ownership и UX-индикация `conflict` должны быть доведены (см. `3301_TODO_LIST.md`).

2. **Тесты не соответствуют коду (частично неисполняемы по API)**
   - Исторический каталог `tests/` устарел/удалён; актуальные автотесты перенесены в `res://3301_/3301_test/`.
   - Контракты `WallData.buy_sides_atomic()`, `to_dict()`, `merge_from_dict()` в текущем `wall/data/WallData.gd` **присутствуют**, но важно держать тесты и документацию синхронизированными по реальному месту и текущему API.
   - Риск: автоматические проверки дают false confidence или не запускаются, если запускать неправильный набор тестов.

3. **Нарушение заявленной атомарности сегментных покупок**
   - Доки декларируют "все или ничего", а `PurchaseManager.commit_bulk_wall_segment_purchase()` делает поэлементные `buy_side()` после предчека.
   - При частичных отказах возможны частичные применения.
   - Риск: финансовая и продуктовая неконсистентность.

4. **Управление секретами/конфигами в опасной зоне**
   - `config/firebase_web_config.json` существует в репозитории (файл недоступен для чтения в анализе из-за ограничений среды), при этом в `.gitignore` он должен игнорироваться.
   - Риск: утечка API key / неправильный процесс секрет-менеджмента.

## Важные (масштабируемость/сопровождение)

1. **`CubeView.gd` как монолит ~1.4k+ строк**
   - Высокая связанность, много режимов/fallback, дублирование input-веток mouse/touch.
   - Сложно писать интеграционные тесты и безопасно вносить изменения.

2. **Избыточная синхронная работа в `_process`**
   - `MainMenu.gd` и `HUD.gd` обновляют UI каждый кадр, даже когда значения не меняются.
   - Риск: лишняя нагрузка и I/O шум (вместе с логированием).

3. **Debug-логика оставлена в runtime-пути**
   - В `scripts/Player.gd` явно включен "временный мгновенный death mode".
   - Поведение может не соответствовать ожиданиям геймдизайна/баланса.

4. **Дубли и рассинхрон терминов**
   - Смешение понятий score / wallet / economy.
   - Часть комментариев и документов описывает неактуальные контракты.

## Вторичные (качество/техдолг)

- Логирование неоднородно (`_log`, `FileLogger`, `print` вперемешку).
- Стиль API в модулях разный (где-то Result-dict, где-то bool без причин).
- Много fallback-кода "на всякий случай", усложняющего чтение.
- Есть битый ассет: `LoadingLevel.tscn` -> отсутствует `LoadingLevel.gd`.

## 3) Документация: что совпадает / устарело / не хватает

### Соответствует коду

- Общая структура сцен и подсистем.
- Описание двух режимов генерации пути.
- Наличие AuthService + FirebaseGoogleAuth + Android-first подхода.

### Устарело или расходится с кодом

- UX конфликтов/ошибок RTDB sync должен быть доведён (см. `3301_TODO_LIST.md` и `3301_RELEASE_CHECKLIST.md`).
- `WallData` модель в документах упоминает поля/операции, отсутствующие в текущем API.
- Таблицы autoload в части документов не включают `EconomyRemoteSync`.

### Не хватает

- Официальной матрицы "что реально работает в прод-режиме, а что прототип/заглушка".
- Контракта атомарности и ошибок для батч-покупок сегментов.
- Явной политики по секретам (где хранить, как ротация, что запрещено коммитить).

## 4) Сверка "заявлено vs реализовано"

### Реально реализовано

- Базовый игровой цикл (MainMenu -> Level -> GameOver).
- Покупки сегментов/платформ локально.
- Wallet sync с RTDB через `EconomyRemoteSync`.
- Path library + chunk streaming механики.

### Реализовано, но слабо описано

- `EconomyRemoteSync` как autoload и его merge-логика по timestamp.
- Временные debug-режимы, влияющие на геймплей (например смерть в `Player`).

### Заявлено, но не подтверждено реализацией

- Атомарность сегментного батча "все или ничего" в текущем API/UX.

## 5) Готовность проекта к MVP

- **Оценка:** **62%**
- **Почему не выше:**
  - высокий риск рассинхрона "доки/тесты/код";
  - невалидированный и фактически неинтегрированный sync сегментов;
  - монолит `CubeView` и слабая тестируемость критического purchase flow.
- **Почему не ниже:**
  - core loop и основные UX-сцены работают как каркас;
  - есть офлайн-first данные, экономика и зачатки облачной синхронизации.

## 6) Список проблем по приоритетам

### Critical

- Нет подтвержденного рабочего pipeline sync сегментов/платформ (`BlackoutSync` не подключен).
- Контракты тестов и `WallData` расходятся.
- Атомарность сегментных батчей не гарантирована.
- Секреты/конфиги потенциально в VCS.

### Important

- `CubeView` перегружен ответственностями.
- Runtime debug-поведение попало в продуктовый путь (`Player` смерть).
- Частые per-frame UI refresh без событийной модели.

### Secondary

- Непоследовательный стиль логирования и ошибок.
- Битые/неиспользуемые ассеты.
- Накопленные комментарии "временных" решений.

## 7) Конкретные предложения (без массового рефакторинга)

1. **Зафиксировать контракт sync**
   - Либо официально отключить `BlackoutSync` и убрать claims в документах.
   - Либо подключить один узкий путь вызова из `CubeView` после успешного коммита покупки + явный статус в UI.

2. **Выровнять `WallData` и тесты**
   - Либо добавить минимальные методы-адаптеры (`to_dict`, `merge_from_dict`, `buy_sides_atomic`), либо обновить тесты под реальный API.
   - Выбрать один контракт и закрепить в документации.

3. **Закрыть атомарность batched segment purchase**
   - Подход: pre-validate all -> reserve budget -> apply all -> rollback on first fail.
   - Минимальный вариант: возвращать детальный result + запрет частичного применения.

4. **Секреты**
   - Удалить конфиг с ключом из git-индекса, оставить только example.
   - Проверить `AuthService` fallback-цепочку и добавить check startup-warning в docs.

5. **Стабилизация `CubeView` без рефакторинга**
   - Вынести только orchestration покупки в отдельный сервис-скрипт (1 слой), оставив UI в `CubeView`.
   - Снизить дубли input-веток через маленькие helper-функции.

6. **Контрольный smoke-набор**
   - Headless/ручной сценарий: main flow + purchase flow + auth restore + wallet sync.
   - Зафиксировать pass/fail чеклист в CI-ready формате.

## 8) SUPER TASK — безопасный MVP roadmap

Каждый этап независим, минимален по изменениям и не ломает текущую работу.

### Stage 1 — Truth Baseline (доки и контракты)

- **Цель:** убрать ложные утверждения и зафиксировать фактическое поведение.
- **Изменить:** документацию по sync/atomic/test contracts.
- **Затрагивается:** `3301_PROJECT_STATE.md`, `3301_SYNC_PROTOCOL.md`, `3301_DATA_MODELS.md`, `3301_TEST_PLAN.md`.
- **Результат:** команда понимает реальный AS-IS, без "магии" в документах.
- **Проверка:**
  - ручная ревизия docs на противоречия;
  - чек "каждое упоминание метода существует в коде".

### Stage 2 — Sync Safety Gate

- **Цель:** безопасно зафиксировать жизнеспособный sync-путь.
- **Изменить:** один официальный путь sync после покупки (или официально выключить sync и пометить feature flag).
- **Затрагивается:** `CubeView.gd`, `scripts/sync/BlackoutSync.gd`, `scripts/purchase/PurchaseManager.gd`.
- **Результат:** предсказуемое поведение sync-статусов (`pending/synced/failed/conflict`).
- **Проверка:**
  - smoke: купить сегмент/платформу -> увидеть итоговый статус;
  - негатив: при ошибке git статус становится `failed`, без silent pass.

### Stage 3 — Atomic Purchases Hardening

- **Цель:** устранить частичные применения батч-покупок.
- **Изменить:** контракт bulk purchase в одном месте (сегменты), добавить result-структуру.
- **Затрагивается:** `scripts/purchase/PurchaseManager.gd`, `wall/data/WallData.gd`, `CubeView.gd`.
- **Результат:** либо весь батч применился, либо ничего не изменилось.
- **Проверка:**
  - тест "один конфликтный сегмент в батче" -> 0 применений;
  - баланс кошелька после fail не изменяется.

### Stage 4 — Test Reality Alignment

- **Цель:** тесты проверяют текущие контракты, а не прошлую версию API.
- **Изменить:** синхронизировать `3301_/3301_test/segment_purchase_tests.gd`, `3301_/3301_test/sync_merge_tests.gd` с реальными методами.
- **Затрагивается:** `3301_/3301_test/*purchase*`, `3301_/3301_test/sync_merge_tests.gd`, при необходимости thin adapters в `WallData`.
- **Результат:** тесты исполнимы и валидируют критические риски.
- **Проверка:**
  - локальный запуск тестов (CLI/editor);
  - отчёт pass/fail без "method not found".

### Stage 5 — CubeView Containment

- **Цель:** снизить риск изменений без полного рефакторинга.
- **Изменить:** вынести orchestration покупок в 1 сервисный слой, оставить UI-код в сцене.
- **Затрагивается:** `CubeView.gd`, новый `scripts/purchase/*service*.gd`.
- **Результат:** меньше связности, проще сопровождать purchase flow.
- **Проверка:**
  - smoke для всех сценариев покупки не меняется функционально;
  - diff фокусируется на одном модуле за раз.

### Stage 6 — MVP Freeze Checklist

- **Цель:** перед релизом иметь контролируемый "go/no-go".
- **Изменить:** финальный checklist + release gates в docs.
- **Затрагивается:** `3301_TEST_PLAN.md`, `3301_TODO_LIST.md`.
- **Результат:** формализованный допуск в MVP.
- **Проверка:**
  - все пункты чеклиста имеют воспроизводимый шаг проверки;
  - нет открытых Critical из этого документа.

---

**Принцип внедрения:** сначала закрыть Critical (Stage 1-3), затем стабилизация и только потом локальные улучшения UX/архитектуры.
